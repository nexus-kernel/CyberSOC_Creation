# EBR security HTML report

The collector creates the report in each completed evidence pack in two HTML editions, with its PowerPoint edition `03-security-report.pptx` beside them. Each HTML edition works offline as a single file with embedded data, styles and graphics. Open it in a browser to view the report, change its depth or print the selected view.

| File | Edition | Who receives it |
|---|---|---|
| `03-security-report.client.html` | Client edition. The report pages, rendered ahead of time, with no presenter notes, embedded data or identifiers. Needs Node.js | The client |
| `03-security-report.pptx` | PowerPoint edition. Speaker notes are talking points from client-visible text only | The client |
| `03-security-report.html` | Internal edition. The same pages with the presenter notes, the evidence review and the collection register | Atmosera only, never the client |

Both HTML editions are written on every run, so there is no edition switch. The SecOps worklist (`04-secops-worklist.md` and `.csv`) is internal too and never goes to the client.

The report follows the navy, cyan and white theme of the EBR decks and the structure of the security slides: a four tile strip, the four tier "How we report posture" block, measured outcomes by pillar, the E, P, N control matrix, delivered and sequenced work with the passwordless transition, and the two Microsoft scores in context. It works for any client regardless of subscription or workspace count.

## Generate from an existing evidence pack

```powershell
./New-EbrSecurityReport.ps1 -EvidencePath './EBR-Evidence_Client_20261008-120000'
```

```powershell
./New-EbrSecurityReport.ps1 -EvidencePath './EBR-Evidence_Client_20261008-120000' -Depth Detailed -ContextPath './client-review-context.json' -OutputPath './Client-Security-Review.html'
```

Generation requires PowerShell 5.1 or later and the adjacent `report` folder. No Azure session, browser automation package, Node installation or Python installation is required to generate or view the internal HTML edition. The client edition needs Node.js, and the PowerPoint edition needs Node.js and pptxgenjs (`npm ci` in this folder, see [Windows setup](#windows-setup-for-the-powerpoint-edition)). Without them the internal HTML is still written and a warning says which editions were skipped. `-SkipDeck` writes the two HTML editions only. With `-OutputPath` the client edition takes the same name ending in `.client.html`, for example `Client-Security-Review.client.html`. `-OutputPath` names the internal edition, so a path that already ends in `.client.html` is refused. The browser must support JavaScript. The completed HTML has no dependency on the original evidence folder.

To change the default for a new collection use `./Get-EbrSecurityEvidence.ps1 -ReportDepth Brief`. Use `-SkipHtmlReport` to collect evidence without generating HTML. A report generation error preserves the collected evidence and returns exit code 2. Re-run the standalone generator after correcting the error.

### Windows setup for the PowerPoint edition

PowerShell 5.1 ships with Windows, so the deck needs only Node.js and pptxgenjs.

1. Install Node.js 16 or later. The current LTS is the safe choice. Open a new PowerShell window afterwards so `node` is on PATH. Without it the generator writes the HTML and warns that the deck was skipped.

   ```powershell
   winget install OpenJS.NodeJS.LTS
   ```

2. In the folder that holds `package.json`, install the locked packages. `npm ci` installs pptxgenjs 4.0.1 and jszip exactly as `package-lock.json` records them. Use it rather than `npm install`, because `package.json` allows any 4.x release and the chart repair in `report/deck-common.cjs` was written for the 4.0.1 workbook bug. Copying an existing `node_modules` folder also works, since every package in it is plain JavaScript.

   ```powershell
   npm ci
   ```

   pptxgenjs is looked up from `report` upward, so keep `report` inside the folder where the packages were installed, or set `NODE_PATH` to a `node_modules` folder that has them. The macOS fallback path in `report/deck-common.cjs` is skipped on Windows.

3. If the scripts arrived in a zip or a download, Windows may block them as unsigned. Allow them for the current PowerShell window only.

   ```powershell
   Set-ExecutionPolicy -Scope Process Bypass
   ```

PowerPoint, Python, LibreOffice and Chrome are not needed to build the deck. They are used only for visual QA. The deck backgrounds are already rendered in `report/assets`. The controls deck (`node report/build-controls-deck.cjs`) uses the same setup.

| 04 The controls that matter | Balanced, Detailed | E, P, N status marks by pillar |
| 05 What comes next | all | Verified delivery, the top three sequenced priorities, the MFA method update |

Rules the deck follows:

- Each subtitle is a takeaway built from the slide's lead metric.
- Response speed is the median time to close for every high severity alert created in the period and closed by collection, the fixed cohort the HTML tiles use. A median under 20 minutes or a 90th percentile over one hour is shown with its note, never hidden or swapped for another cohort. The time to close table shows every severity with time to acknowledge beside it.
- Severity increases stay in the HTML presenter notes. Open alerts appear only as the closed and open counts in the detection statement, the open sentence in its narrative and the referral sentence on the operations slide, which also shows how closed alerts were classified. Neither says resolved, since a closure can carry no classification (Oct 16, 2026).
- Foundational controls below E appear on the gaps panel and first in Now, as Atmosera's fix. The deck calls them gaps against the baseline, never drift or a regression, and never says a control was configured at build: the evidence holds the current reading only (Oct 14, 2026). Defender for Identity sensors and domain controller telemetry need a license and sensors from the client, so they are defense in depth and go to Later with the licensing ask (Oct 16, 2026).
- A Conditional Access control reads In force when an enabled policy covers every user on every application in every condition, Mostly enforced (marked P, with the sign-in ratio beside it) when the enabled policy stops short of that, by selecting its users or applications or by a platform, risk level, device filter or location condition, and at least half of the measured sign-ins still satisfied it, and Not in force otherwise. The grade rests on the measured ratio. The note says how the policy is scoped, from the `ScopeReason` the evaluator records (Users, Applications, UsersAndApplications, UsersOrApplications or Conditions). UsersOrApplications marks one enabled policy that selects its applications for all users beside another that selects its users, and the note then names both kinds rather than one. A missing or unknown reason falls back to the general sentence. A policy scoped to selected applications is never described as requiring the control on every application.
- Backup coverage is two items. When fewer than half of the virtual machines carry a protected Azure Backup item, and the reading is not a small sample, Now carries "Backup coverage validation": the DP.5b figure and a recommendation to confirm with the client which machines without one persist, to separate confirmed gaps from agreed exclusions. In a Now column already holding three items it is named on the column's Also line. It is shared work at no cost and needs no decision, so it adds no ask. The Azure Backup extension stays in Later with its ask, since it adds recurring cost. From half to 89 percent, or on a small sample, Later carries the extension alone. Half is read from the counts, not the rounded percentage, so 500 of 1,001 is under half (Oct 18, 2026).
- Workload protection names the resource types outside Standard plan coverage, for example "24 AI services not covered", on the gaps panel, the roadmap and the register.
- A ratio control with fewer than 10 resources, such as 2 of 2 machines patched, never stands as a win or leads a pillar in the posture matrix. The control itself still reads in the register.
- On the measured outcomes slide, a pillar narrative that does not fit its row loses sentences from the end, but the endpoint coverage sentence and the EW.1-GAPS reconciliation are never cut when machines are not reporting. The row first drops the other sentences, then takes the short headline without its remainder clause, then gives the measure column to the story (the kept coverage sentence carries the figure), then sets the story in 9 pt. When even that cannot hold them, as with the largest EW.1-GAPS result (the seven other reasons beside the third-party reason split across all nine product labels, 16 groups), the row keeps its measure, shows the kept sentences that fit and "The full reading continues on the next slide.", and a "Measured outcomes by pillar, continued" slide carries the pillar's headline and whole narrative. No row runs into the next.
- Read access is asked for only where the collector's token was not permitted to read the evidence (the `AccessGap` flag the builder derives from the manifest detail). Service errors are Atmosera's to resolve and never become an ask. A service that answers that the tenant is not onboarded or not licensed sets `NotOnboarded` instead, so the control reads Not in force where the collection shows domain controllers (NB.10 devices or DR.4 events). Without that positive evidence it stays ungathered: NB.10 reads Azure virtual machines only and DR.4 needs Defender for Identity telemetry, so an empty read never proves a cloud-only tenant.
- The deck never prints `(null)`. Ungathered controls read "Not gathered" with a dash chip.
- Containment is never claimed, and neither is impact. The tactic count is of true positives whose recorded tactics include Exfiltration or Impact, from the tactics the builder embeds on every OUT.4 row, and every surface reads "carried an exfiltration or impact tactic", never "reached": the tactic is a detection-time label on the alert, not an investigation finding, and the collector's own OUT.4 note holds that a zero data loss statement needs each flagged closing comment reviewed. The collector's ExfilOrImpactTactic flag also fires on a Collection tactic, so a pack whose rows carry no tactics (an older builder, or a flagged row whose tactics could not be read) keeps the flag count and reads "carried a collection, exfiltration or impact tactic" instead. A true positive is a closure classification, so the surfaces say "classified as true positives by the SOC", never investigated. The handling strip on the confirmed threats slide names only the steps the evidence records (detect, triage, classify) and closes with "impact confirmed only from reviewed investigation records", so neither the strip nor the speaker notes say a confirmed threat was investigated, assessed for impact or closed. No client-facing string says "no impact", "did not reach" or "reached" unless the context file carries a reviewed `Impact` record (see below). Until it does, the threats table caption, the HTML threats block and the speaker notes read "Based on the tactics Sentinel recorded on the alerts, none of the confirmed threats carried an exfiltration or impact tactic. Additional investigation evidence is required to confirm whether any data exposure or business impact occurred." The 90th percentile is creation to recorded close, so it reads "Nine in ten triaged and closed within", never investigated or resolved.
- A presenter note records that an indicator-based true positive (a Log4Shell IP or domain indicator match, for example) confirms the indicator was observed, not that exploitation or compromise occurred, and counts the example titles that name an indicator.
- The hardening count of members without MFA is written against the same members as the MFA at sign-in control, for example "14 of 194" beside a control reading "180 of 194", so the two reconcile at a glance.

Charts are native PowerPoint charts, so they stay editable. Speaker notes are talking points built only from text the client already sees in the HTML, such as pillar narratives and control descriptions. The presenter notes are never copied in, so the deck can be sent to the client after the review.

## Vocabulary and copy rules

Sentinel incidents are presented as **alerts** in every client-facing sentence. SecurityAlert records are presented as **detections**, so the two counts never collide. Dates are written out, for example "Jul 1 to Sep 30, 2026". Visible copy contains no arrows, emoji or semicolons, and the greater-than sign is not used in prose. HTML, CSS and JavaScript keep their required syntax. Reviewed context receives the same normalization.

Planned work is worded as a recommendation. Completed, implemented and verified come only from reviewed `Delivered` records, and scheduled, approved and in progress only from a reviewed `Actions` record for the item (see below). Without a record, roadmap evidence, asks and takeaways never say an item is scheduled, approved, completed, implemented or verified: the critical vulnerability item reads "7 critical exploitable findings. Atmosera recommends validating the affected workloads and agreeing remediation or compensating controls with the owners inside the patch cadence.", the drift panel reads "Atmosera recommends closing each gap first.", and the roadmap scope line recommends staging each enforcement in an audit or report-only mode where the control supports one. The MFA method update outcome is measurable: every affected user registered on a replacement method before February 1, 2027 (July 1, 2027 for Global Administrators and external users), the fallback tested, and no rise in failed sign-ins after enforcement. The update never says the users need to update their MFA method or still rely on text message or voice, since IA.2 records use, not registration. Passkeys are the recommended target, and the update is never framed as a passwordless programme.

## How figures are selected

| Measure | Rule |
|---|---|
| Alert scope | An alert is a Sentinel incident that opened an Atmosera ticket, identified by a ticket reference in its comments or closing comment. Informational severity is excluded. Detections are limited to those linked to these alerts. The collector applies this scope (version 1.6 or later, `-TicketPattern`). Packs collected without it receive a presenter note and count every incident. When P0.1-XDRDUP reads no Defender XDR alert in Sentinel, the operations page, its slide notes and the A4 Alerts fact say that alerts investigated only in other platforms, including Microsoft Defender XDR, are not included. A count above zero shows that some Defender XDR alerts reach Sentinel, never that all do, so the same surfaces say alerts investigated only in other platforms, including the Microsoft Defender XDR portal, are not included and Defender XDR alerts are counted where Sentinel received them. When P0.1-XDRDUP is missing, partial or unreadable they say the routing was not read and that such alerts may not be included, never that they are. Detections name only the sources OUT.5 holds |
| Alerts triaged | Alerts created in the period (OUT.1). When automation rules closed at least half of the closed alerts, the headline excludes automation closures and the automation count is shown as a supporting line |
| Open alerts | Never shown on the executive page and never a roadmap priority. The detection statement leads with the closed and open counts, for example "80 of 100 alerts closed, 20 open at collection", and its narrative reads "20 were pending client action, confirmation or continued investigation at collection". The operations page describes them as items referred to the client for action or confirmation under the agreed notification process, together with investigations still in progress. OUT.1 holds the open count only, so they are split into "awaiting client action or confirmation" and "still in progress with Atmosera" only from a reviewed `OpenAlertNote` record in the context file (see below). Age buckets are not shown. OUT.1 reads each alert created in the period at its latest state at collection, never at the period's end, so an alert open on the last day and closed before collection counts as closed, and every surface says "at collection" or "by collection", never a period-end or reporting cutoff state. The presenter note carries the raw count |
| Closed share | Shown in the outcomes tier, as "Alerts closed", only at 90 percent or more. Always shown on the operations page. Every surface says closed, never resolved, since OUT.1 records a closure, not how it was resolved, and unclassified closures are named beside the closed count in the detection narrative and on the operations page |
| Response timing | One fixed cohort: every high severity alert created in the alert period and closed by collection (`OUT.2`, row High, which filters on the creation time and reads each alert's latest closed state, so an alert created on the last day and closed after it counts, and one created before the period does not), automation closures included, so the cohort and the period never change with the result. Its median time to close and 90th percentile always supply the two tiles, and its median time to acknowledge (`MedianTriageMin`, creation to the first status change from New, by an analyst or an automation rule, so an alert closed straight from New counts that close) sits beside them in the operations table. A median under 20 minutes or a 90th percentile over one hour is presented with a visible note, "covered in the review", and a presenter note, never replaced by another cohort or period. Fewer than 5 closed high severity alerts withholds the timing, and the reason is listed with the unmeasured evidence. When automation rules closed any of the cohort, the operations table adds two labelled rows: analyst-handled (`OUT.2-ANALYST`) and closed by automation rules. The collector records no timing for automation closures alone, so that row carries the count only. The deck's time to close table shows every severity from `OUT.2` with automation closures included, and every median and 90th percentile. With a reviewed `ResponseTargetMinutes` in the context file, a line compares the median and 90th percentile with the agreed target (under it, over it, or about the same within a minute) and says that close times are recorded in whole minutes and the percentiles are estimates. `OUT.2` holds no per-alert close times, so no surface gives a share of alerts that met the target. Without the field no target line is printed. Closure is not containment. The presenter notes carry the cohort, its figures and the notes applied |
| Monthly volume | Presented as work absorbed by the SOC, stacked by severity in one hue. No first-to-last comparison is written for the client. A high severity increase becomes a presenter note. When the number of Sentinel workspaces whose alert records span a month varies across the months the chart shows (the last 12), the HTML chart, the operations slide and its notes add the record dates and the count per month, for example "The alert records retained in 3 of the 6 Sentinel workspaces start after Jul 1, 2026. Alerts are counted in the month they were created. Workspaces whose retained alert records span the whole month: 3 of 6 in Jul 2026, 6 of 6 in Aug to Sep 2026." The counts come from the first and last SecurityIncident record of each workspace (P0.1-BY-WORKSPACE, matched on its ID, else its name, or P0.1 in a pack with one Sentinel workspace, which the collector reads without a breakdown). The line cites the result it read. A workspace counts in a month only when its records run from the 1st to the last day, and a workspace with no alert record stays in the denominator. Consecutive months with the same count are grouped, and a month OUT.3 has no row for ends a group. A first record shows the earliest alert record still held, not when collection began, since a quiet workspace or a retention shorter than the window also starts late, OUT.3 also counts each alert in the month it was created, from its latest retained record, so an alert can fall in a month before its workspace's first retained record. The copy therefore states retained record dates, never which workspaces an alert came from, and draws no conclusion about activity. A partial reach reading, or unreadable record dates, adds nothing |
| Confirmed threats | Three measures are kept apart. Confirmed malicious activity is the true positive classification count from OUT.1, labelled "Confirmed threats" and described as alerts the SOC classified as true positives. Confirmed security incidents have no collected or reviewed source, so no surface prints one. Confirmed business impact comes only from the reviewed `Impact` record in the context file and is never derived from tactics. The exfiltration or impact line counts the OUT.4 tactics only, never incident comments, and reads "carried", never "reached". The examples are OUT.4 true positives with an attack stage, grouped by screened alert title with the alert count, highest severity, attack stages and the months they span, up to five groups, highest severity first. Withheld titles and true positives with no attack stage, such as a service limit warning, stay out of the examples and are counted in the presenter notes. With no examples the table is left out, and the HTML block and the slide still carry the true positive count and the impact statement |
| Status marks | E at 90 percent or more, P from 50 to 89, N below 50. Verified configurations such as the Conditional Access controls, anti-phishing, Safe Links, Safe Attachments, threat intelligence, analytics rules in every Sentinel workspace and domain controller telemetry read as In force. An enabled Conditional Access policy that stops short of every user on every application in every condition reads Mostly enforced (P) when the sign-in ratio behind it is 50 percent or more, with the ratio shown beside it and the note naming how the policy is scoped. The percentage bands apply to ratio controls: a policy scoped by users, applications or conditions reads P however high its ratio, since the policy is not in force everywhere. E is a band, not the absence of exceptions: a ratio control at E that still leaves resources out shows the count as exceptions on the register, for example "1 exception" under the figure of an E control in the HTML and after its label on the deck register (which steps down to 10 pt when a column would not otherwise fit), and no headline, win or narrative says every, all or none for it. A Conditional Access control in force whose excluded accounts signed in shows them the same way, for example "2 excluded accounts signed in" (issue #27). A ratio control is on a small sample when it counts fewer than 10 resources, or, where the collector records an excluded count (EW.10-EXCLUDED for patch cadence), when more machines are excluded than assessed (Oct 18, 2026, issue #24). It keeps its mark and counts toward enforced and measured, and the register flags it, "E, small sample" under the figure in the HTML and "small sample" beside the figure on the deck register (under it when the two do not fit one line), so the flag never lengthens a label and the register keeps its fit in a small tenant where every endpoint ratio is flagged. Every tier total that holds one names it beside the total, for example "19 of 28 foundational controls enforced (1 on a small sample)": the executive summary tier, the KPI or summary win, the posture takeaway, the pillar tier counts in the HTML, and the matrix, all pillars, pillar outcome and register counts on the deck. It never leads a pillar and never stands as a win. A verified configuration (In force) is never on a small sample. Such a pillar leads with the ratio and the remainder, for example "Endpoint detection covers 88 of 89 eligible Azure virtual machines, with 1 remaining" or "Secure transfer is required on 36 of 37 storage accounts, with 1 remaining". The data protection statement names key material only when Key Vault soft delete is complete as well. The detection statement "Every alert closed with a documented disposition" is earned only by a complete DR.10 reading of every workspace beside an OUT.1 reading with no open alert and no unclassified closure. Open alerts at collection lead it with the closed and open counts from OUT.1, for example "80 of 100 alerts closed, 20 open at collection". Otherwise a DR.10 reading of every workspace that leaves closures undocumented, or sits beside unclassified closures, gives its ratio with its window, for example "97 of 100 alerts closed in the last 30 days carry a documented disposition". The triaged count from OUT.1, for example "100 alerts triaged Nov 1, 2025 to Sep 30, 2026", leads when DR.10 is missing, unavailable, ungathered, holds no closures in the last 30 days, or is partial because a workspace failed or was excluded. The pillar source line cites OUT.1, and DR.10 beside it only when DR.10 gives the statement, so a partial DR.10 ratio never leads the pillar. OUT.1 shows nothing about closing comments, so it never earns every on its own. The narrative keeps triage, closure, open status and classification apart: "The SOC triaged 110 alerts associated with the managed security service", then "By collection, 91 were closed", the open sentence and the unclassified closures. The DR.10 win reads "alerts closed in the last 30 days with a documented disposition" and names the unclassified closures beside it as alerts created in the period and closed by collection (Oct 16, 2026). No pillar letter grade is generated |
| Secure score movement | Measured from the first month of the continuous export (POS.7) to the current score (POS.1), so the points and the percentage on the page reconcile. A current score below the first month shows no gain. Two readings are compared only when they use the same scoring model and the same maximum (Oct 16, 2026). A different maximum means the evaluated scope or the scoring changed between them, so the score reads as current state and the presenter notes or evidence review name both readings. A classic Defender for Cloud reading is never compared with a risk-based Cloud Secure Score reading |
| Benchmark controls | POS.5 rows for one edition of the Microsoft cloud security benchmark only: the unversioned name, else a versioned name that is not a preview, else the latest preview. A second edition or the CSPM scaffold assigned beside it is not added in, and named standards that are not the benchmark never stand in for it, so the meter is left out without a benchmark edition. Legacy rows with no standard name count as a whole |
| Device scope | Every device measure (endpoint detection, sensors, anti-malware, tamper protection, host firewall, credential protection, Remote Desktop, network protection, NTLMv2, directory signing, vulnerability assessment, exploitable findings) reads Azure virtual machines only (Oct 14, 2026). Collector 1.14.0 drops other endpoints at the source, and the report leaves the Other device rows of older packs out, so a workstation fleet never inflates a figure such as network protection to the thousands |
| Endpoint detection | Azure virtual machines reporting to endpoint detection is onboarded plus machines covered by a third-party endpoint detection product, over the machines eligible for endpoint detection. The reasons come from EW.1-GAPS (collector 1.14.0): a machine covered by CrowdStrike Falcon or another product named by `-EdrVendorPattern` is protected, a network virtual appliance, a deallocated machine and an unsupported operating system leave the denominator, and a machine Defender for Endpoint has never discovered joins it. The note under this row and under the sensor row states every reason, so the two figures reconcile on the page. An empty EW.1-GAPS result reads as every machine onboarded with an active sensor only when the onboarding and sensor figures are both complete. The presenter notes carry the Resource Graph inventory count beside the Defender count |
| Configuration presence | Some controls read that a configuration is present, not the protection it delivers, and their labels and notes say so (Oct 18, 2026, issue #26). Network segmentation (NB.1) reads "Workload subnets with a network security group or firewall route" and the pillar says the subnets "have a network control configured", with the note that the rules and the traffic they permit are not evaluated. Workload protection (DR.2) is read from the subscription plan configuration, so its label, its note, the pillar narrative and headline, and the deck name it a plan-level estimate. Safe Links and Safe Attachments read In force when at least one policy is configured with the features on, and their labels say the policy is set, since the recipients a policy applies to, its exceptions and the Safe Links rule state are not read. Managed disk encryption at rest (DP.3) is on by default in Azure with platform-managed keys, so it stays in the register with that note and is never a win. Encryption at host is graded separately |
| Ungathered controls | Shown on the controls page as (null) with no status mark, excluded from the executive summary tiers, and listed in the presenter notes with the reason. Controls with no applicable resources in scope are omitted |
| Controls without evidence either way | Shown as N/A with no status mark and excluded from every count. Used when the evidence was gathered but holds nothing to judge, for example no device code sign-ins and no Conditional Access policy inventory. Listed in the evidence review |
| Location-based sign-in access | IA.4-LOCATION replaced the share of sign-ins Conditional Access evaluated (IA.4) on Oct 12, 2026. It reads In force when an enabled policy in IA.8-POLICIES has a country or named location condition, blocks access or requires MFA, and covers all users and all resources. Scoped and report-only policies read Not in force. Packs with only the flattened IA.8 inventory read (null), since it never recorded locations. Exclusion counts stay in the presenter notes |
| Detection and response tiers | Since Oct 16, 2026 analytics rules (DR.9) and threat intelligence ingestion (DR.7) are foundational, since the Atmosera standard rule set and ingestion are switched on at build, so a gap reads on the gaps panel and first in Now. DR.9 reads In force only when every Sentinel workspace in scope has at least one enabled analytics rule, from a complete read: a workspace read with none reads Not in force, and a partial read stays ungathered. It does not identify which rules are Atmosera's, since they carry no naming convention, and the enabled of total count is context in its note, so disabled rules never create a gap. Domain controller telemetry (DR.4) and Defender for Identity sensors (DR.11) are defense in depth, since they need Defender for Identity licensing and a sensor on each domain controller from the client and do not apply to cloud-only tenants. Their gaps share one Later item. The licensing ask is raised only when the Defender for Identity sensor control reads N, since a telemetry gap beside healthy sensors is an ingestion fault rather than missing licensing, and it takes its turn with the other defense in depth asks. Two controls moved each way, so the pillar's tier counts are unchanged |
| Endpoint sensors | Active sensors among the Azure virtual machines onboarded to Defender for Endpoint. Workstations and network devices such as firewalls are not part of the measure, and rows whose platform names a firewall operating system are dropped for older packs too. The EW.1-GAPS reasons are repeated in its note |
| Patch cadence | Machines whose tags record patching as waived or client owned leave the measure at collection (collector 1.14.0, `-PatchExclusionTagPattern`). The note states how many were left out, from EW.10-EXCLUDED, and that Atmosera reviews these tags with the client at each business review, never that a tag was confirmed. The evidence review repeats the count and asks the presenter to confirm each tag is still intended. The register row names both populations, for example "2 assessed · 18 excluded by tag". Machines Update Manager never assessed are not in EW.10, and its machine scope (Azure and Arc machines with a patch assessment) differs from the DP.4 inventory (Azure virtual machines and scale sets, appliances left out), so no not-assessed count is derived from it |
| Blob containers | DP.1-CONTAINERS (collector 1.11.0) grades the defense in depth row Blob containers closed to anonymous access on each container's own access level, read in every storage account. Containers readable anonymously today, and accounts that could not be listed, go to the presenter notes and evidence review, never the client page |
| Conditional Access controls | IA.1, IA.1-ADMINPORTAL, IA.3 and IA.3-DEVICECODE read the policy state from IA.8-POLICIES (or the flattened IA.8 inventory for packs before collector 1.10.0) and the per-account sign-in detail from IA.8-SIGNINS, through `report/Get-EbrCaEvaluation.ps1`. Only the per-control counts are embedded, as IA.8-CA. Multifactor authentication required at sign-in (IA.1) reads In force when an enabled policy requires multifactor authentication on every application for all users and is not narrowed to a platform, risk level, device filter or location, or when security defaults are on (Oct 14, 2026). Multifactor authentication at admin portal sign-in (IA.1-ADMINPORTAL) reads In force when an enabled policy requires it on the Microsoft admin portals or on every application, for all users or for the administrator roles. A scoped, report-only or missing policy reads Not in force. The sign-in ratio from IA.1 and IA.1-ADMINPORTAL moves to the note and the pillar page, and a ratio below E with the policy in force is explained in the presenter notes. Without a policy inventory the sign-in ratio grades both as before. For IA.3 and IA.3-DEVICECODE the block policy decides the status. An enabled block policy for all users, or security defaults for legacy authentication, makes the control In force, and a scoped, report-only or missing policy makes it Not in force. Sign-ins show only whether an account got past the policy. Sign-ins by excluded accounts are described as coming from accounts excluded from the policy, with "Atmosera reviews these exclusions with your team at each business review". Nothing in the evidence records that an exclusion was approved, so no client sentence calls it approved or confirmed (issue #27). Successful sign-ins the policy did not evaluate go to the presenter notes, and legacy attempts that failed without a block are listed per protocol in the SecOps worklist with the password spraying hint. Without a policy inventory the control reads In force only when Conditional Access blocks are recorded and no sign-in succeeded, Not in force when a sign-in succeeded, and N/A otherwise. Only error 53003 counts as a Conditional Access block, so legacy attempts that failed without one, such as a wrong password or a locked account, are never presented as blocked |
| MFA coverage population | In a federated tenant, members whose only sign-ins reused a device session that no Conditional Access policy checked are not evaluated and leave the denominator of Multifactor authentication required at sign-in (IA.1). Members whose only MFA evidence is an earlier MFA sign-in in the same session (collector 1.13.0) count as covered. The grade stays on the members evaluated, and the client surfaces say who it covers: the control note and the identity pillar narrative state how many members signed in, how many could be evaluated, how many of those showed MFA on their own sign-ins and how many by inference from an earlier MFA sign-in in the same session, and how many were not evaluated. The HTML register reads the share as "of members evaluated", the hardening tier counts "Evaluated members without MFA", the deck register carries the split on the detail line, and no deck row cuts it from the pillar slide. A tenant with no member unevaluated and none inferred keeps its plain reading, with no zero split. In a federated tenant the multifactor priority first reviews the identity provider's authentication policy and the federatedIdpMfaBehavior setting of each federated domain, then extends Conditional Access. The presenter notes keep the explanation |
| Cloud score | Computed from points. With at least two valid monthly readings, the continuous export trend (POS.7) is shown in both HTML and PowerPoint whether rising, flat or declining. With less history the current score stands alone. A gain line compares the current POS.1 score with the first trend reading and appears only for a positive change between readings with the same maximum. The card and the deck appendix name the model (classic Defender for Cloud secure score), the source (Azure Resource Graph), the scope as a subscription count, never a subscription ID, and the read date. POS.1 adds the points of each subscription, while the Azure portal weights subscriptions by their healthy and unhealthy resources, so the presenter notes say the portal percentage can differ when more than one subscription is in scope. Where the next points are shows each control's healthy resources of those it assesses from POS.3, and no count when either figure is missing or both are zero. Microsoft documents the classic control score within each subscription or connector as the score per resource, the maximum over the healthy and unhealthy resources, times the healthy resources, so a control gains points before it completes (learn.microsoft.com, Secure score in Defender for Cloud, Jun 30, 2026). POS.3 adds each control's points and resource counts across subscriptions, so with more than one subscription the caption says the share of resources healthy can differ from the share of points earned. The Microsoft measurement model explainer remains alongside the scores: scope, weighting and model changes can move the percentage without a change in controls |
| Tenant score | Requires a dated portal reading in the context file, or the Microsoft Graph reading (POS.6). The card and the deck appendix name the model (Microsoft Secure Score), the source (Microsoft Graph or a reviewed portal reading), the scope (the Microsoft 365 tenant) and the read date. The device score is never substituted |
| Priorities | Ranked in a fixed sequence: critical exploitable findings, multifactor coverage, the MFA method update, endpoint coverage, anti-malware configuration, workload protection, logging, encryption at host, backup, storage transport, key protection, segmentation, platform integrity. The top three are shown, the rest expand. The order is proposed for agreement at the review, never presented as scheduled or approved |
| Data gaps | Missing, failed, unavailable, manual and empty evidence never become a favorable zero or 100 percent. Duplicate cross-workspace alerts withhold every alert figure until reconciled |

Alert activity uses the recorded period. Identity and endpoint evidence retains its source lookback, generally the last 30 days. Configuration and score readings are point-in-time measurements.

## Add reviewed context

Copy `report/context.example.json`, enter the exact client and tenant from the pack, then populate the supported fields. Each field below is an example of the format, not client evidence.

```json
{
  "ClientName": "Example Client",
  "TenantId": "example-client-tenant-id",
  "ServiceStartDate": "2023-08-15",
  "TenantScore": {
    "Current": 58.68,
    "Max": 100,
    "ReadDate": "2026-10-08",
    "Source": "Defender portal capture saved with the October review",
    "Previous": 53.2,
    "PreviousMax": 100,
    "PreviousReadDate": "2026-07-10",
    "Categories": { "Identity": 50.8, "Device": 61.3, "Apps": 59.5, "Data": 71.4 }
  },
  "Delivered": [
    {
      "Title": "Storage transport baseline",
      "Outcome": "Validated the approved transport settings across the agreed storage scope.",
      "Reference": "CHG-12345",
      "CompletedDate": "2026-09-18",
      "Pillar": "Data protection"
    }
  ],
  "Actions": [
    {
      "Key": "critical",
      "Status": "Scheduled",
      "Owner": "Client infrastructure team with Atmosera",
      "TargetDate": "2026-11-30",
      "Verification": "BKL.1 reads no critical exploitable finding at the next collection.",
      "Reference": "CHG-12400",

    }
  ],

    "Reference": "ZD 9900200",

  },

```

`ServiceStartDate` enables the "Months of managed security" tile. `Previous`, `PreviousMax` and `PreviousReadDate` add the tenant score movement line, in percentage points. Without `PreviousMax` the maximum comes from the POS.6-TREND snapshot dated `PreviousReadDate`, and without that the movement line is omitted and the evidence review says so. The line is printed only when the earlier maximum equals `Max`, since Microsoft widens the maximum over time and a wider maximum is a different evaluated scope. Optional `PreviousModel` names the scoring model of the earlier reading, Microsoft Secure Score when absent, and a reading from another model is never compared. A refused comparison reads as current state and the evidence review names both readings. `Categories` are percentages and add the category bars on the posture page. A delivered item needs a title, outcome, reference and a completion date inside the alert period. Incomplete entries appear in the evidence review instead of on the client page. `Impact` is the reviewed data exposure and business impact determination for the period's true positives: `Confirmed` is the number of true positives with confirmed data exposure or business impact (0 when the review found none), `Reviewed` is the date the closing comments and tickets were reviewed, `Reference` is the ticket or record that holds the review, and `WindowStart` and `WindowEnd` are the alert period the review covers, copied from the pack's `00-parameters.json`. All five are required. The window must match the pack's alert period, `Reviewed` must be on or after `WindowEnd`, and `Confirmed` cannot exceed the OUT.1 true positive count, so a context file reused from an earlier period never carries a determination forward to later true positives. A record that fails any check is omitted with an evidence review note naming the reason. With the record the threats caption, the HTML threats block, the executive tile and the outcomes tier print the determination with its reference and date, and a confirmed impact withdraws the tactic win from the summary. Without it the report prints the tactic count and asks for additional investigation evidence, and the evidence review says so. The generator checks structure and date scope but cannot verify the referenced ticket, portal capture or impact review. `OpenAlertNote` is the reviewed status of the alerts OUT.1 counts as open at collection: `AwaitingClient` is the number awaiting client action or confirmation, `InProgress` the number still in progress with Atmosera, and `Reviewed`, `Reference`, `WindowStart` and `WindowEnd` follow the `Impact` rules. All six are required, the window must match the pack's alert period, `Reviewed` must be on or after `WindowEnd`, and the two counts must add up to the OUT.1 open count, so a record reused from an earlier period never splits a later count. With the record the detection narrative, the operations page and the operations slide split the open alerts, and the pillar source line, the operations page and the operations slide's speaker notes cite the record. A record that fails any check is omitted with an evidence review note naming the reason, and the surfaces keep the combined sentence. `ResponseTargetMinutes` is the agreed time from alert creation to recorded close for high severity alerts, as a whole number of minutes above zero. With it the operations page, and the operations slide's speaker notes, compare the timing cohort's median and 90th percentile with the target. A value that is not a whole number above zero is omitted with an evidence review note, and without the field no target line is printed. The comparison counts no alerts against the target, so it is not an SLA attainment figure. `Actions` is the reviewed status of a roadmap item or an ask, one record per item. `Key` names the item: `drift` (the foundational gaps), `critical` (critical vulnerability remediation), `methods` (the MFA method update and its ask), `access` (the read access ask), `backupcheck` (the backup coverage validation in Now), or a roadmap catalog key from `report/report-story.js` (`idp`, `phish`, `consent`, `workload`, `logging`, `kvrbac`, `diskenc`, `containers`, `vulnassess`, `segment`, `windows`, `backup`, `vmplatform`, `pim`, `allowlist`, `sharing`, `mdi`), and the same key matches the roadmap item and its ask. The `detect` item was split on Oct 16, 2026: a record that tracked vulnerability assessment takes `vulnassess`, and one that tracked analytics rules or threat intelligence takes `drift`, since those are foundational gaps now. A record that still names `detect` is omitted with an evidence review note that says so. The `backup` item was split on Oct 18, 2026: `backup` keeps the Azure Backup extension in Later and its ask to agree which machines persist and approve backup cost, and `backupcheck` is the new validation step in Now. A reviewed `backup` record keeps its status on the extension and its ask only, and never on the validation. A record that tracked confirming which machines persist, with no backup cost approved, moves to `backupcheck`. `Status` is one of `Proposed`, `PendingValidation`, `AwaitingApproval`, `Approved`, `Scheduled`, `InProgress` or `Verified`. `Reference`, `Reviewed`, `WindowStart` and `WindowEnd` are required, the window must match the pack's alert period, and `Reviewed` must be on or after the posture read date, so a record from an earlier review never carries a status forward to this collection's findings. `Owner`, `TargetDate` and `Verification` (how completion is checked) are optional, except that `Scheduled` needs a `TargetDate`, and `Verified` needs a `Delivered` record in the same alert period with the same `Reference`. A second record for the same key, an unknown key or status, or a record that fails any check is omitted with an evidence review note naming the reason. With a record the roadmap item's evidence line carries the status, owner, target date, reference and review date, and the drift panel names the status of the foundational fixes. An approval ask, or the MFA method update ask, whose record reads `Approved`, `Scheduled`, `InProgress` or `Verified` is no longer a decision: it leaves the decisions slide and the executive summary before the four-ask limit and the count, so the next pending ask takes its place, and the decisions slide's speaker notes name it with its status. An ask whose record reads `Proposed`, `PendingValidation` or `AwaitingApproval` stays, with the status on a line under its body. The read access ask stays whatever its record says, with the status under it, because no status shows the permission was provisioned. It leaves only when a collection reads the evidence. The drift panel's status line is cut with three dots when its reference would run into the first gap, and the slide's speaker notes carry it in full. On the deck the card text steps down from 13 pt to 10 pt to hold that line, and an owner or reference too long even then is cut with three dots, owner first. The speaker notes keep the full attribution. A record whose key matches no item on this roadmap is not shown. The generator checks structure and dates but cannot verify the referenced change or ticket. The context file accepts no overrides for computed metrics.

## Presenter notes

Open **Presenter notes** in the toolbar of the internal edition, `03-security-report.html`, before the review. The section lists every figure that needs a prepared answer (open alerts, closure classification, automation share, high severity trend, workspace coverage, score movement), the response timing cohort with its figures and the notes applied, the controls that were not measured, outstanding portal readings and the collection register. ## Client edition

`03-security-report.client.html` shows the same pages as the internal edition, with the same figures, status marks, tiers and priorities. A test holds the two equal on the offline fixture, page by page and at every depth. The builder renders the pages ahead of time with `report/build-client-report.cjs`, which runs the report model and renderer in Node.js against the same data, the way the browser runs them in the internal edition. The client file then carries:

- The rendered pages, the styles and `report/report-controls.js`, the toolbar script for the depth selector and the print button. Nothing else.
- No embedded data and no report model. So it holds no presenter notes, evidence review, timing rationale or collection register. It also holds none of the wording of those notes in the report code, none of the results, fields or context records only they read, and none of the subscription, workspace, tenant or other identifiers in the data.
- No GUID. Every GUID on the rendered pages becomes the same `[id 1]` placeholder wherever it appears, in any case and even between other hexadecimal characters. That covers the subscription ID inside a default workspace name and a GUID in a context `Reference`. The builder refuses to write a client edition that still holds a GUID, report data or the presenter notes.

Evidence IDs and read dates stay in the source lines, since they carry no identifiers. The subscription and workspace counts stay in the scope line, and workspace names stay on the posture page. The client edition needs Node.js, like the PowerPoint edition. Without it only the internal edition is written, with a warning, any client edition from an earlier run is removed, and the internal edition must not be sent instead. The PowerPoint edition is unchanged. It is built from the internal data, and its speaker notes never carry the presenter notes.

## Controls standard for executives

```powershell
./New-EbrControlsStandard.ps1
```

Writes `docs/The Controls That Matter.html` and `docs/The Controls That Matter.pptx`: page 04 on its own, as a standard rather than a client reading. Both are informational. They outline every control by pillar and tier with the reading that grades it, explain the tiers and the E, P and N marks, count the controls per pillar and close with an invitation for feedback. They do not ask for sign-off and carry no measure IDs, change list or page footers, and they hold no client data. The control list comes from `report/report-model.js` run on an empty pack in standards mode, so both always match the client report. Set the title and version in `report/controls-standard.json`, then regenerate after any change to a control, its tier or its measure.

The deck is built by `node report/build-controls-deck.cjs [output.pptx]` (pptxgenjs, `npm ci` if it is missing). It has a title slide, the two tiers, grading, controls by pillar as a native chart, one slide per pillar and tier with a card per control and speaker notes, and a closing feedback slide. Its backgrounds (`report/assets/deck-title.jpg`, `deck-band.jpg`) are rendered from the report background by `node .report-build/make-deck-assets.cjs`. `-SkipDeck` writes the HTML only. `node .report-build/check-standard.cjs` checks the HTML headlessly and writes screenshots and a PDF to `.report-build/standard`.
